# DIGGER 3D — Three.js One-Shot Coding Benchmark

You are an autonomous senior gameplay programmer, Three.js engineer, technical artist, game designer and audio programmer.

Build a complete polished browser game inspired by the classic 1983 arcade game **Digger**, reimagined as a modern 3D underground arcade diorama.

Do not write a design document.

Do not stop at scaffolding.

Do not ask questions.

Build the game until it is playable from title screen to game over.

The core design principle is:

> **2D arcade simulation, 3D presentation.**

The gameplay remains grid-based and faithful to Digger-like mechanics, while Three.js renders the board as a tactile miniature underground world.

The benchmark is primarily testing whether you can correctly implement several interacting game systems in one autonomous run:

1. Persistent terrain excavation.
2. Grid-based arcade movement with input buffering.
3. Gold-bag state machines and falling/crushing mechanics.
4. Dynamic enemy navigation over a changing map.
5. Distinct Nobbin and Hobbin behavior.
6. Rechargeable ranged attack.
7. Enemy spawning, cherry bonus mode and scoring.
8. Separation between deterministic simulation and 3D presentation.
9. A coherent and attractive Three.js visual result.
10. A finished, robust project rather than a prototype.

A visually impressive game with incorrect mechanics is a failure.

A mechanically correct game with simple but coherent visuals is acceptable.

A mechanically correct game with polished 3D presentation and strong arcade feel is excellent.

Create a real project using:

Do NOT use:

- Phaser
- Babylon.js
- PlayCanvas

- Godot exports
- Rapier

## C3. Offline

The game must run with zero runtime network requests.

Do not fetch:

- textures
- models
- sound effects
- music
- fonts
- APIs
- remote JSON
- CDN dependencies

Generate the visuals procedurally with Three.js primitives and local code.

Generate audio with WebAudio.

---

## C4. Deterministic simulation

Use ONE seeded PRNG for every gameplay-random decision.

Seed:

`0xD166E2`

This includes:

- enemy decisions
- transformation timing
- spawn variation
- visual procedural decoration where relevant

Restarting a level with the same seed must recreate the same logical state.

---

## C5. Gameplay simulation is authoritative

CRITICAL ARCHITECTURAL RULE:

> Three.js object transforms are NEVER the source of truth for gameplay.

Every gameplay object must have a logical simulation state independent of its Three.js mesh.

For example:

```ts
interface EntityState {
  col: number;
  row: number;
  direction: Direction;
  state: EntityMode;
}
```

The simulation decides:

- position
- collisions
- terrain
- pathfinding
- deaths
- score
- falling
- spawning
- level completion

The renderer only visualizes this state.

Never determine gameplay by checking approximate `mesh.position`.

Never use Three.js raycasting for ordinary gameplay collision.

Never use visual interpolation as simulation.

---

## C6. Grid + rendering separation

Logical coordinates:

```text
column
row
```

Visual coordinates:

```text
x = column * CELL_SIZE
z = row * CELL_SIZE
```

The vertical Y axis is for presentation only.

Examples:

```text
terrain top: y = 0
player: y ≈ 0.4
emerald: y ≈ 0.5
gold bag: y ≈ 0.5
falling bag animation: variable y
particles: variable y
```

The game must remain logically two-dimensional.

Target stable 60 FPS on a mainstream desktop GPU.

Use:

- `InstancedMesh` where appropriate
- object pools for common effects
- sensible particle caps
- no per-frame garbage in hot loops where practical

Clamp `devicePixelRatio <= 2`.

Clamp extreme delta time after tab switching.

# 2. CAMERA

## CAM1. Fixed gameplay camera

Use a fixed 3/4 perspective camera looking down onto the board.

Suggested perspective:

- yaw approximately 35–45°
- pitch approximately 45–60°
- whole gameplay board visible

The player should understand the whole level at a glance.

---

## CAM2. No free orbit during gameplay

Do NOT allow free camera rotation during normal gameplay.

A freely orbiting camera creates:

- hidden tunnels
- ambiguous movement
- occlusion problems
- camera-relative control complexity

These do not improve the benchmark.

---

## CAM3. Camera effects

Allow restrained camera effects:

- tiny positional shake on gold-bag impact
- stronger shake on player death
- tiny zoom/focus pulse on bonus activation
- slight level-start camera settle

Gameplay readability always takes priority.

# 3. WORLD PRESENTATION

The viewer sees:

- earth blocks
- carved tunnels
- stones
- emeralds
- bags
- enemies

# 4. TERRAIN

## T1. Logical grid

Use approximately:

```text

```

## T2. Terrain cells

Each cell stores at least:

```text

```

## T3. 3D earth

Represent solid earth using chunky cube-like or rounded-block geometry.

Preferred implementation:

`THREE.InstancedMesh`

## T4. Earth appearance

Do not use flat brown boxes.

Create visual variation procedurally with:

- slightly varied block scale
- vertex/color variation
- small stones
- dirt speckles
- subtle roughness variation
- darker side faces

Do not generate thousands of unnecessary meshes.

---

## T5. Excavation

When Digger enters solid earth:

- logical cell becomes excavated
- corresponding visible earth disappears or retracts
- dirt particles burst backward
- small pebbles jump
- excavation sound plays

The excavation remains permanent for the rest of the level.

---

## T6. Tunnels

Excavated cells should reveal a dark tunnel floor.

Use subtle tunnel detail such as:

- darker soil
- wheel tracks
- disturbed dust
- occasional stone fragments

Do not dynamically boolean-subtract geometry.

Removing/hiding terrain cells is the intended solution.

# 6. PLAYER — DIGGER

## D4. Digging animation

- wheels work harder

- headlamp vibrates slightly
- excavation sound plays

---

## D5. Lives

Start with:

- touched by a dangerous enemy outside bonus mode
- crushed by a falling gold bag

Death sequence:

1. gameplay collision disabled
2. Digger spins or jolts
3. small explosion/dirt burst
4. machine collapses
5. short pause
6. level resets

Preserve:

- score
- lives
- current level

# 8. GOLD BAGS — CRITICAL

Gold bags are one of the benchmark's defining systems.

Implement them as explicit state machines.

Required states include:

```text
RESTING
PUSHING
WOBBLING
FALLING
LANDING
BROKEN
COLLECTIBLE
```

You may add more states if useful.

---

## B1. Horizontal push

Digger may push an intact resting bag horizontally.

Requirements:

- next cell must be valid
- no blocking object beyond it
- push only horizontally
- visual movement is interpolated
- logical transition remains discrete

Give bags a sense of weight:

- slight Digger compression
- scraping sound
- dust
- slow start / eased finish

---

## B2. Unsupported bag

If support below an intact bag disappears:

```text
RESTING
↓
WOBBLING
```

Wobble for roughly:

`0.5–0.8 seconds`

Then:

```text
WOBBLING
↓
FALLING
```

---

## B3. Wobble

The 3D bag should:

- shake left/right
- tilt
- slightly compress
- release tiny dust

This warning must be obvious.

---

## B4. Falling

A falling bag descends vertically through excavated cells.

The logical simulation tracks cell transitions.

The 3D mesh visually accelerates downward.

Use fake gravity/easing.

Do NOT use a physics engine.

---

## B5. Crushing

A falling bag kills:

- Digger
- Nobbins
- Hobbins

that occupy its path.

Enemy crush score:

`250`

A crushed character must have a visible squash/impact animation.

---

## B6. Break condition

Track the number of complete grid rows fallen.

If fall distance is:

`1 row`

the bag remains intact.

If fall distance is:

`2 or more rows`

the bag breaks open when landing.

---

## B7. Break effect

Breaking should be one of the game's strongest visual moments.

Use:

- short hit-stop
- camera shake
- leather fragments
- gold nuggets
- dust ring
- bright flash
- metallic crash

Create collectible gold.

---

## B8. Gold collection

Broken gold is worth:

`500 points`

Digger must physically reach it.

Enemies may reach/destroy/deny gold if your rules require it.

---

## B9. Chain correctness

Handle situations involving:

- bag over player
- bag over enemy
- bag over another bag
- bag pushed into shaft
- player removing support while moving
- enemy digging beneath bag
- bag falling while level state changes

Never allow contradictory bag states.

# 13. CHERRY BONUS MODE

This system is mandatory.

---

## CH1. Cherry appearance


## CH2. Cherry

`1000 points`

---

## CH3. Bonus mode

Cherry activates temporary bonus mode.

Early-level duration:

approximately `10–15 seconds`

During bonus mode:

- Digger kills enemies by contact
- enemies become frightened
- enemies try to move away
- enemy appearance changes
- board lighting shifts
- music changes
- HUD shows BONUS
- Digger headlamp/glow intensifies

---

## CH4. Enemy chain score

Enemies eaten during the same bonus period score:

```text
200
400
800
1600
3200
...
```

Display value at the enemy location.

---

## CH5. Frightened presentation

Frightened enemies should visibly change.

For example:

- cyan/blue material
- wide eyes
- faster leg animation
- backward glance
- small sweat particles

---

## CH6. Expiry

When bonus time expires:

- normal enemy behavior returns
- palette returns

- chain counter resets

No enemy may remain permanently frightened.
