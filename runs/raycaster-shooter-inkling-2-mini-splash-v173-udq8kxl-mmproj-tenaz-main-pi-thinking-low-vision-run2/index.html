What was checked

  • Runner final state COMPLETE_WITH_GAPS on 25 November 13:09:03.166 UTC. Bootstrap passed its three steps first time (22 requirements, R22 'playable in a browser' manual; 11 tasks). T001 to T014 passed verify and review on their first attempt; T015 (barrel half-hidden at spawn) and T016 (controls hint overflow) were sent back once each and accepted on attempt 2. Three replans added nothing.
  • Runner events: 44 sessions, none stopped or failed; no watchdog actions, reverts, context compactions, provider errors, capacity limits or engine retries. No reply stopped at the output limit: the stop reasons are 399 tool use and 44 stop, and the largest reply is 10,245 tokens of the 16,384 allowed.
  • Configuration: the UD-Q8_K_XL thinking-low setup with vision. Pi 1.6.0 over RPC with the openai-completions provider splash, thinking low, text and image input, a 131,072-token context window and max_tokens 16,384; Tenaz main 3f43405 with defaults plus --vision, temperature 1.0, generic engine, sandbox off. Against the runs without vision, the go script adds only --vision, and the engine start script only --model-dir, --mmproj and --draft-model (plus comments and the two path variables they use); the stop and launch scripts, brief and Tenaz binary are byte-identical. Tenaz's preflight reported reasoning, cache, tools and vision true; its image check answered 'red blue'.

All are screenshots the model took of its own game with Playwright.
  • Engine metrics: one Splash process wrote 789 Done summaries over both vision runs. Requests 1 and 2 are Claude's own image check before this run's init, 3 to 8 vision run 1's preflight, 9 to 340 vision run 1, 341 to 346 vision run 2's preflight and 347 to 789 vision run 2. This run's 443 proxy records match summaries 347 to 789 one-to-one, in order, contiguously and uniquely by (prompt, output, cached). For all 44 sessions the matched summaries' fresh input, cached and output tokens equal the usage Tenaz journaled. TTFT comes from Splash's 'TTFT of request' lines.
  • Memory: Tenaz's 193 host samples report memory pressure level 1 (normal) throughout. Wired memory went from 44.7 GiB at the first sample to a maximum of 52.4 GiB, and free memory fell to 0.11 GiB at its lowest. Swap use ranged from 14.3 to 14.4 GiB, already about 14 GiB before the run. Tenaz sampled Splash's Python parent, not its engine, so no engine footprint is recorded.
  • Configuration against vision run 1: the engine start and stop scripts, go and launch scripts, brief and Tenaz binary are byte-identical, and the pinned run state differs only in paths, times and results. Splash was not restarted: its process from vision run 1 served this run, with the prefix cache and memory state that run left behind.
  • `verify --all` on a clean clone of the final commit 964f9e9 with the run's node_modules: 17 of 17 passed, as Tenaz recorded. Model-written checks that test state, math and file presence, not playability.
  • Played by Claude with Playwright in Chromium's new headless mode, against the run's build served by Vite, holding keys. Map: 32 by 32 cells. Spawn (5.5,4.5) faces east down a one-cell corridor (row 4, columns 2 to 8) at the door (9,4), 3.5 cells ahead, drawn as a wooden door; a barrel at (7.5,5.3) in an alcove shows partly behind the wall edge. Space opens doors within 2 cells of the door's centre, so the player has to walk up to it first; it then let the player through into the one room (columns 10 to 29, rows 2 to 11).
  • The open door is still drawn closed: src/raycaster.js stops every ray at a 'D' cell whatever the door's state, so after Space the player walks through a door that is still drawn. The same happened in the UD-Q4_K_M thinking-high run.
  • Mouse look: a click calls canvas.requestPointerLock, and mousemove turns the player only while the canvas holds the lock, which is correct in a normal browser. Headless Chromium refuses pointer lock, so turning was tested with the lock faked: mouse moves turned the player. A/D strafe; no key turns.
  • Combat: the enemy at (15.5,6.5) chases the player; faced and shot, it lost a hit point per shot and died on the third. Dead enemies are not drawn (src/main.js adds only alive enemies to the sprite list), so it vanishes instead of falling and staying down as the brief asks. Health stayed 100: no code lowers it.
  • Look: the canvas is drawn at 320 by 200 and scaled to fill the window with crisp pixels; brick walls along the spawn corridor, stone walls in the room, a wooden door, a tiled floor and a textured ceiling. The minimap is a mostly white panel with the room as a dark block and no view cone (the open T017), and the controls hint is drawn across the middle of the screen, over the view.
  • Public artifact: `vite build --base ./` of the final commit 964f9e9 in the clean clone; its JavaScript bundle is byte-identical to the run's own dist, and its index.html differs only in the script path. Plain canvas code; the capture fetched only from the local server. Screenshot: a fresh headless capture of the published build at 960x600, in the doorway of the room, with the enemy close on the right.

Limits of this evidence

Completion is the runner outcome. The second run of the vision setup (Inkling 2 Mini as Unsloth's UD-Q8_K_XL GGUF on Splash 1.7.3 with its BF16 vision projector and the DFlash2 drafter at a 128K context, Pi thinking low with image input, temperature 1.0, Tenaz main 3f43405 with --vision), with nothing changed and Splash not restarted. The model looked at screenshots more than in run 1 (44 images in 13 sessions against 13 in 4), and its reviewers used them to send back visible defects, but the game is clearly weaker than run 1's: the open door is drawn closed, there is one room, the dead enemy vanishes and the minimap is broken. With the two runs without vision, it shows that vision catches some visible defects, yet the spread between runs at temperature 1.0 is still large. Decode median 68.4 tok/s, against 68.5 in vision run 1.
