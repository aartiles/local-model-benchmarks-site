Session partial Local run

A separate configuration with Pi's output limit raised to 65,536 tokens, not comparable with the 16,384-token runs. The model finished a complete project with a final report; the TypeScript check, 28/28 self-tests and production build pass and the simulation plays. The 3D board renders inverted: the dirt is invisible, the visible blocks are the tunnels, digging has no visible effect and enemies are hidden inside blocks. The scene is also very dark.

Play build ↗Compare attempts →Measurements ↓

What was checked

  • tsc --noEmit passed, npm run test reported 28/28 PASS and npm run build produced the JavaScript bundle when rerun after the session.
  • Browser check with the in-game debug overlay, about 50 s of scripted input: the digger moved on the grid and dug, collected an emerald, fired and recharged; enemies spawned (2 of 6) and a death took lives from 3 to 2 with the level reset the prompt asks for. No page errors.
  • Hands-on play by the operator: digging had no visible effect and enemies never appeared. Cause in src/render/terrain.ts: update() shrinks every cell marked solid, not only newly dug cells, so all dirt disappears within about 0.25 s while tunnel cells keep full-size blocks; enemies move through tunnels and are hidden inside them. The simulation is unaffected, which is why the self-tests pass.
  • One response produced 19,436 output tokens, above the 16,384 limit that stopped runs 2 and 3.
  • The model's final report states it had no browser and did not inspect screenshots. A full level, level transition and game over were not played in the browser.

Limits of this evidence

Splash 1.4.0 (Homebrew) served the model with --max-context=131072 under the name Qwen3.8-Flash-Next-Splash-Q2_0. The startup log reports 128K context, routed experts resident in memory (32,402 MiB) and the per-layer n-gram table streamed from its file (27,465 MiB on the SSD), and warns that with --verify-rows auto greedy and seeded outputs can differ from run to run for this MoE target. Splash had released its weights after 600 s idle before runs 2, 3 and the 64K-output variant and restored them in about 8.4 s before the first request, which is inside the first request's TTFT. Splash reports TTFT and decode rate, not a standalone prefill rate, draft acceptance or peak memory. The only change from runs 1-3 is the Pi provider's maxTokens (65,536 instead of 16,384); the Splash process, model and prompt are the same.
