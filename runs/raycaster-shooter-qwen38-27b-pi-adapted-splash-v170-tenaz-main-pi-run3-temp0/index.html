What was checked

  • Runner final state COMPLETE on 19 November 17:40:57.209 UTC: 12 tasks done, none pending. Bootstrap steps spec and verify passed on the first attempt; the task step failed once (requirement R20 had no task) and passed on the second (12 tasks, 23 requirements). Final review cycle 1 returned ACCEPT with verify passing and all 23 requirements covered, none by hand. `verify --all` passed 22 of 22 model-written checks again after the run; not a hidden acceptance suite.
  • Configuration: identical to run 2 (same brief, checkpoint, engine scripts, Tenaz main 2f1b04c binary, Pi 1.4.0, thinking off, vision, generic engine, Tenaz defaults, sandbox off) except temperature 0 instead of 0.8; the two run.json parameter blocks differ only there. Launched with --allow-weak-engine. The preflight reported tools=false and vision=false: its probes got 2 to 4 output tokens each from an engine started seconds before (run 1's first preflight on a fresh engine read the same), while every run session called tools and the model read images with no refusal.
  • Runner events: one session ended early: 033-builder-T012 (a visual polish pass) was steered at turn 40 and stopped at 60 turns, and a fresh session finished the task in 12 turns, not counted as an attempt. T002 and T011 needed a second attempt after a CHANGES review; the other ten task reviews returned ACCEPT. Two replans added no tasks. No response stopped at the output limit.
  • Played on 19 November by the operator in the Claude desktop browser pane and in Chrome, after Claude found that the pane refuses pointer lock (a pointerlockerror on click), so neither mouse aim nor firing work there. The operator's verdict: a worse finish than run 2, ammo runs out with no reload, and enemies do not die.
  • Causes, checked by Claude in the source and in Node against the built modules: hasLineOfSight in src/enemies.js compares a ray parameter from 0 to 1 with a distance in cells, so it keeps stepping past the target into the next wall; on open floor it returns true at 3 cells and false at 5, so shots beyond about 4 cells miss and distant enemies never chase. At 2 cells, three shots kill. Both the click and the mousedown handler fire while the pointer is locked, so every click spends 2 of the 30 bullets. There is no reload, no ammo pickup and no damage code, so enemies never attack. The controls hint renders as 'WASD MO E MOUSE AIM CLICK SHOOT S ACE DOOR': the bitmap font has no V or P.
  • Must have results: walking, strafing and wall collision work; straight walls; brick, stone and wood textures plus a panelled door; textured floor and ceiling; side and distance shading visible, not measured; Space opens the spawn door; left click fires with a muzzle flash and lowers the ammo count. Partly met: the barrel in the spawn view stands beside the door, not behind a wall edge; enemies react and die only at close range.
  • Vision: no image refusals. The model read five different images: its three spawn, turn and door captures and two contact sheets it built itself.
  • Engine metrics: a fresh Splash process serving only this run. Its 391 summaries are 4 preflight requests and 387 run requests. 387 of the 388 proxy records match a Splash summary one-to-one and in order by (prompt, output, cached); the unmatched one is the empty record of the aborted turn. Per session, the totals equal the Pi usage Tenaz journaled.
  • Memory: Tenaz's 206 host samples run from start to end. Wired memory went from 26.6 GiB at the start to about 46 GiB after 30 minutes (median 45.2, maximum 47.3). Memory pressure was normal in 178 samples and at warning in 28, all between 17:03 and 17:12 UTC; nothing measurable was swapped in. The engine's wired memory was lower than in run 2, so the warning came from the rest of the machine (about 1.3 GiB more compressed memory, with ten Claude Code sessions open); Chrome was closed most of the time.
  • Public artifact: the reviewed static build (vite build --base ./ from the final project commit 818ffa7, unchanged source) and its spawn view at 1280x720. The prompt is the author's and is not republished; the project, raw logs, journal and sessions stay in the ignored local archive.

Limits of this evidence

Completion is the runner outcome. A repeat of run 2 on the same day with temperature 0 instead of 0.8 and everything else unchanged. It finished in about half the time and wrote about 56% of run 2's output tokens, but its game plays worse, and its own checks did not catch the faults. One execution per temperature: the difference is not attributed to temperature. The playthrough was the operator's; the causes were found by Claude in the source.
