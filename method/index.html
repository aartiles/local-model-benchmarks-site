Run protocols

Most runs here are one-shot. A single task prompt is submitted to the model through a coding agent, and I do not intervene, steer the session, or hand-edit the result. The published build is whatever the run produced.

The archive also includes long-horizon runs, in which a deterministic runner rather than a model takes one brief through many fresh agent sessions, with the plan and project state kept in files. The runner below describes it. Manual continuation, setup drift and runner changes during a run are recorded on the run sheet.

That protocol is what makes the builds comparable as artifacts: each one is an honest answer to the same prompt. It is not what makes their measurements comparable. Every workload in this archive records one repetition, so a figure such as a decode rate describes one session rather than a stable property of the model or engine.

The runner

Since 20 October the long-horizon runs use Tenaz, an open-source runner, public since 22 October and released as 0.1.0 on 27 October. It is a program, not a model. It has the local model plan the brief and write a verify script, splits the work into tasks, and builds each task in a fresh coding-agent session. A task is committed only when its checks pass and a new reviewer session agrees, and a final reviewer judges the result against the brief. The run’s state lives in the project, so a run can pause and resume; on an existing repository it works on its own branch.

Tenaz grew out of the runs in this archive, in four steps. Each step followed a run that showed what the step before could not do.

Metric definitions

These are the measurement names used across the run sheets, with the statistic each one reports. Where a run recorded a different statistic for the same quantity, that run sheet says so in its own row.

Metric · What it reports
MetricWhat it reports
Decode · per-request medianThe middle per-request generation rate across the session’s requests. Sensitive to short requests and to cache state.
Decode · output-weightedTotal output tokens divided by the summed per-request decode time. Weights long generations more heavily than the median does.
Prefill · medianThe middle prompt-processing rate across requests. Includes cache reuse, so a cached prompt inflates it.
MTP acceptanceThe share of drafted speculative tokens the model accepted. A property of the draft configuration and the text, not of raw speed.
TTFT · cachedRequest-start to first token when the prompt prefix was already cached. Recorded only where the engine logged it.
Cache hit ratioCached input tokens as a share of presented input tokens.
Session elapsedWall time from the first request to the final response. Includes coding, tool calls and recorded checks — it is not generation time.
End-to-end output rateOutput tokens divided by task wall time, including reasoning, tool calls and waiting. Deliberately not model decode speed.
Peak KV checkpointThe largest key/value checkpoint observed in unified memory during the run.
Cumulative inputInput tokens summed across model calls. Repeated conversation context can be counted more than once.

Which figures cannot be compared

Four distinctions account for most of the apparent contradictions between run sheets. Each one is a different question, not a different answer.

Apparent comparison · Why it does not hold
Apparent comparisonWhy it does not hold
Output-weighted decode vs. median decodeDifferent statistics of the same quantity. The TensorFold run reports a median of 22.9 tok/s; the Sushi runs report output-weighted means in the mid-30s. Neither is wrong, and neither converts to the other without the underlying per-request rows, which are not published.
Local decode vs. Codex end-to-end rateThe Codex figures divide output tokens by total task wall time, so reasoning, tool calls, generated tool output and waiting are all inside the denominator. A local engine decode rate has none of that. The cloud run records state this directly.
Prefill across runsPrefill figures include cache reuse, and recorded cache hit ratios range from 90.23% to 95.17% across these runs. A run with more reuse reports a faster prefill for reasons that have nothing to do with the engine.
Session elapsed across runsSession time includes coding, tool calls, recorded checks and any backend failure. The TensorFold session contains a recorded 25,718-second outage, so its raw wall time is not an effective elapsed time; that run sheet publishes both figures.

What this archive does not establish

  • No model ranking. One run per workload cannot rank anything. A completed run is not a better run; it means the build finished and its recorded checks passed.
  • No repeatability. Every workload here records a single repetition. The LLMProbe suite measured each scenario once and is explicitly indicative.
  • No peak-memory comparison for the inference suite. Peak RAM was not sampled during the LLMProbe A/B, so the two engines cannot be compared on memory.
  • No general context ceiling. The MLX-Serve 64K prefill was rejected by its memory-admission policy. That describes the tested cold-prefill scenario, not a maximum context for either engine.
  • No image-model comparison. Four runs render a video and three make their own pictures with a local image model, one run per setup. They show what one setup produced, not which image model or engine is better.
  • No thermal, power or sustained-load data. Long-duration memory pressure and battery behaviour are not covered.
  • Checks were transcribed, not rerun. The verification bullets on each run sheet are transcribed from the session log during archiving. They were not re-executed against the published build.
