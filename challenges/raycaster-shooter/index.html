Task requirements & full brief

Each attempt is a single execution, and the setups change more than one thing at once, so the cards compare whole setups rather than isolate a setting. The two Qwen 3.8 27B pi-adapted runs on Splash are the same setup run twice on one afternoon: both finished in two to three hours, against about seven for Qwen 3.8 Flash Next on Sushi, with memory pressure normal throughout while the Mac stayed in use. Flash Next is the more capable model; the pi-adapted setup reached a game at the same level, faster and with more room left on the machine, which makes it a candidate for work planned and checked by a frontier model. Measurements are on the run sheets. No transcripts are published.

  • DDA raycasting on a 24x24 grid with textured walls, floor and ceiling, fisheye correction and shading.
  • Billboard sprites clipped by a depth buffer: barrels, pillars and enemies.
  • Sliding doors opened with Space; enemies that chase, flash when hit and fall on the third hit.
  • A fixed spawn view: a closed door 4 cells ahead and a barrel partly hidden behind a wall edge.
  • A Playwright screenshot script, and a model that looks at its own screenshots.

How to read this comparison

Compare the generated builds and the checks recorded for each attempt. There is no normalised quality score, and the cloud task’s cumulative token totals and end-to-end rate include repeated context, reasoning, tool calls and waiting — they are not comparable with local per-request decode or prefill rates. The method page sets out which figures can and cannot be set against each other.

Attempts run with Tenaz used the open-source runner at github.com/aartiles/tenaz. It plans the brief into tasks, builds each in a fresh agent session and accepts it only when its checks pass and a reviewer agrees. The method page describes it and the runners before it.
